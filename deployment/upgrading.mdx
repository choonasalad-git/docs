Every ERP version update brings changes to the base application—new DAC fields, renamed graph methods, refactored business logic, and occasionally the removal of deprecated features. Your customizations depend on the ERP's public API surface, so an upgrade that looks routine from the application administrator's perspective can silently break compile-time references or, worse, introduce subtle data issues that only appear at runtime. Following a structured upgrade process keeps your customizations healthy and your users productive after every ERP release.

## Pre-upgrade checklist

Complete all of the following steps on your development instance **before** applying the ERP update to UAT or production.

<Steps>
  <Step title="Export and archive the current customization package">
    Navigate to **Customization > Customization Projects**, select each project, and export a package (`.zip`) for every project. Each package contains a `ProjectMetadata.xml` manifest that records the complete list of artifacts and their version at the time of export. Store these archives in a safe location—your version control system is ideal. These snapshots let you recover the exact pre-upgrade state if things go wrong.
  </Step>

  <Step title="Read the ERP release notes for breaking changes">
    The ERP vendor publishes release notes and an upgrade guide with each version. Search them specifically for:
    - **DAC field removals or renames** — any field your DAC extensions reference that has changed
    - **Graph method signature changes** — event handler parameter types and graph method names that have been refactored
    - **Assembly or namespace restructuring** — classes that have moved to different namespaces or assemblies
    - **Deprecated APIs marked for removal** — warnings from previous versions that have now become hard breaks

    Make a list of every breaking change that affects your codebase before you start the upgrade.
  </Step>

  <Step title="Upgrade a dedicated development instance first">
    Apply the ERP update to a development or sandbox instance that mirrors your production data schema. Never perform an untested upgrade directly on production. Use this instance to discover and fix all compatibility issues before they reach users.
  </Step>

  <Step title="Attempt to publish and record all errors">
    After the ERP update is applied, navigate to **Customization > Customization Projects** and attempt to publish. Record every error and warning in the publish log. This gives you the full scope of changes required before you start modifying code.
  </Step>
</Steps>

## Common upgrade issues

### Changed base DAC fields

The most frequent upgrade issue is a base ERP DAC field being renamed, split into multiple fields, or removed entirely. Your DAC extension may reference the old field name, causing a compile error.

```csharp
// Before upgrade — references a field that was renamed in the new ERP version
public class SOOrder_Extension : PXCacheExtension<SOOrder>
{
    // OldCustomField was renamed to NewCustomField in the base DAC
    [PXDBString(50)]
    public string OldCustomField { get; set; }
}
```

Fix the extension to use the new field name and update every BQL query and event handler that referenced the old name. If the field was removed entirely from the base DAC, move the field definition into your own DAC extension rather than referencing the base.

### Renamed or refactored graph methods

Graph methods (such as action delegates, event handlers, or helper methods on a base `PXGraph`) are occasionally renamed or their signatures are changed. A common pattern is that an event handler parameter type changes from a concrete type to a generic type.

```csharp
// Compile error after upgrade: base method signature changed
protected virtual void SOOrder_RowSelected(PXCache cache, PXRowSelectedEventArgs e)
{
    // e.Row was previously typed as SOOrder; now it is 'object' and must be cast
    SOOrder row = (SOOrder)e.Row;
}
```

Review the ERP upgrade guide for method signature changes and update your event handler signatures to match. Use your IDE's **Go to Definition** on the base graph type to confirm the current expected signature.

### Removed or relocated features

Some ERP upgrades replace an entire subsystem—for example, a legacy approval workflow might be replaced with a new unified workflow engine. If your customization hooks into the old subsystem, you must rewrite it against the new API. The compile errors in this case are often numerous but follow a single root cause: one missing namespace or removed base class.

<Warning>
  DAC extensions that add columns to a table whose corresponding base DAC field is removed can cause **silent data issues**. The column remains in the database, the extension property still compiles (because it references the extension's own field, not the base field), but any business logic that used to populate it is now broken. After an upgrade, audit every `PXDBField` in your DAC extensions against the current base DAC to confirm the underlying column is still meaningful.
</Warning>

## Resolving compile errors after an upgrade

Work through compile errors systematically rather than trying to fix everything at once.

1. **Fix missing namespace / assembly references first.** If a base class or interface has moved to a new assembly, update the project references. All downstream errors caused by the unresolved type will disappear at once.
2. **Fix DAC field references next.** Search your entire codebase for the old field name and replace it. Use your IDE's find-and-replace with case sensitivity enabled to avoid partial matches.
3. **Fix graph method signatures.** Update event handler signatures and override signatures to match the current base class.
4. **Fix BQL queries last.** BQL is strongly typed, so a renamed DAC field causes a cascade of errors in every query that uses it. Once the DAC is correct, the BQL errors are straightforward to resolve.

After each category of fix, attempt a compile (either via **Validate** in the Customization Projects screen or by building the project in Visual Studio) and confirm the error count is decreasing before moving on.

## Testing strategy after an upgrade

<CardGroup cols={2}>
  <Card title="Re-publish on dev first" icon="wrench">
    Confirm a clean publish with zero errors on the development instance before touching UAT or production. A clean publish does not guarantee runtime correctness, but it eliminates the class of issues that would prevent the application from starting.
  </Card>
  <Card title="Run through key workflows" icon="list-check">
    Execute every business workflow that your customization touches—creating records, running actions, triggering automation. Watch for runtime exceptions in the application trace log (Tools > Trace) even if the UI appears to work correctly.
  </Card>
  <Card title="Verify data integrity" icon="database">
    For customizations that write to the database, spot-check that records created before and after the upgrade have consistent field values. Pay special attention to fields that were affected by the base DAC changes.
  </Card>
  <Card title="Test on a data copy of production" icon="copy">
    Before upgrading production, restore a recent production database backup to your UAT instance and re-run all tests against real data. Edge cases that never appear in dev data are common in production datasets.
  </Card>
</CardGroup>

## Using the compare and merge tools

The Customization Project editor includes a **Compare** tool that shows the difference between two versions of a project—useful for understanding what changed between your pre-upgrade export and your post-upgrade working project.

1. Open **Customization > Customization Projects** and select the updated project.
2. Click **Actions > Compare with Package** and select the pre-upgrade `.zip` archive you saved earlier.
3. The compare view highlights every artifact that differs. Use this to confirm you have addressed all breaking changes and have not accidentally lost any customization items during the upgrade.

If you maintain multiple separate projects that must all be updated, use **Actions > Merge Projects** to combine them into a single project for testing. This makes it easier to identify cross-project conflicts that the upgrade may have introduced.

<Tip>
  After a successful upgrade, immediately export a new package archive and commit it to your version control system. Tag the commit with both the ERP version and your customization version (for example, `erp-2024.1-custom-v3.1`). This creates a clear audit trail that future developers can use to understand which customization version works with which ERP version.
</Tip>
