Packaging lets you capture the complete state of a Customization Project—source code, screen definitions, database scripts, and sitemap entries—into a single portable `.zip` file. You can then hand that file to a client, a deployment pipeline, or a colleague, and they can import it directly into their ERP instance without manually recreating any artifacts. Packaging is the primary mechanism for moving customizations between environments (Dev → UAT → Production) and for distributing reusable components across multiple ERP installations.

## Version numbers and the Package Level field

Every Customization Project has a **Package Level** field—an integer that acts as a version stamp for the package. The platform uses this number to detect whether an incoming package is newer or older than the version already installed on the target instance.

- Increment **Package Level** every time you export a package intended for distribution. A common convention is to align it with your own versioning scheme (for example, version 2.3 of your customization → Package Level 23).
- If the imported package has a **lower** Package Level than the installed project, the import dialog shows a warning. You can still proceed, but doing so intentionally downgrades the installed customization.
- The Package Level is stored in `ProjectMetadata.xml` and is visible in the **Customization Projects** list, making it easy to audit which version is running on each instance.

## Handling package conflicts on import

A conflict occurs when the package contains an artifact that already exists on the target instance and the two versions differ. Common scenarios include:

- A developer on the target instance has made local modifications to a screen that the incoming package also modifies.
- Two separate customization projects define the same DAC extension field with different attributes.
- A DB script in the package has already been partially applied by a previous, incomplete import.

For each conflict, the import dialog gives you three choices:

| **Use Package Version** | Overwrites the target version with the incoming artifact. Choose this when the package is the authoritative source of truth. |
| **Keep Current Version** | Ignores the incoming artifact and keeps what is on the target instance. Choose this when local changes must be preserved. |
| **Merge (manual)** | Imports both versions side by side so you can manually reconcile them in the Customization Project editor. Use this for complex conflicts involving code files. |

<Warning>
  Choosing **Keep Current Version** for DB scripts can leave the schema out of sync with the code. If the incoming code expects a column that the skipped script would have created, the customization will fail at runtime with a missing-column error. Always reconcile DB script conflicts carefully.
</Warning>

## Using version control alongside package export

<Tip>
  Treat package export as a **release artifact**, not as your primary version control mechanism. Store your raw project source files (the contents of the Customization Project editor) in a Git repository and use package export only when you need to deliver a tested build to another instance. Commit after every meaningful change, tag commits that correspond to exported packages, and include the Package Level in your tag name (for example, `v2.3-pkg23`). This gives you a full history of changes with the ability to produce a distributable package from any tagged commit.
