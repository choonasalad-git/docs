A Data Access Class (DAC) is the single source of truth for a custom table: it defines the database schema, the field-level validation rules, the UI display names, and the relationships to other entities — all in one C# class file. Once you add the DAC to your customization project and publish, the platform creates the corresponding SQL table automatically. This guide walks you through every step from creating the file to verifying the table in the database.

<Steps>

### Create the C# class file in your project

Open your customization project in Visual Studio (or the in-browser Code Editor). Inside the project's `DAC` folder — create it if it does not exist — add a new C# file. Name the file after the entity it represents, for example `RSSVRepairOrder.cs`.

At the top of the file, add the standard ERP namespace imports:

```csharp
using System;
using PX.Data;
using PX.Objects.AR;
using PX.Objects.IN;
```

Wrap your class in your company's custom namespace so it does not collide with any built-in class:

```csharp
namespace MyCompany.MyProject
{
    // DAC class goes here
}
```

<Note>
Always prefix your DAC class name with a short company or project identifier (for example `ACME`, `RS`, or `MyComp`). The ERP namespace is large and evolving; a prefix prevents name collisions when the product ships a class with the same business name in a future release.
</Note>

### Declare the DAC class

Inside your namespace, declare the class as `public` and implement the `IBqlTable` marker interface. Add the `PXCacheName` attribute directly above the class declaration to give it a human-readable name for cache diagnostics and error messages, and add `Serializable` so the platform can serialize the cache between requests:

```csharp
[Serializable]
[PXCacheName("Repair Order")]
public class RSSVRepairOrder : IBqlTable
{
    // Fields go here
}
```

The `IBqlTable` interface has no members — it is purely a marker that tells the BQL engine this class represents a database table.

### Define the primary key field (PXDBIdentity)

Every custom table needs a primary key. The recommended approach for custom tables is an auto-incrementing integer identity column. Declare a field class and its backing property following the DAC field pattern:

```csharp
#region OrderID
[PXDBIdentity]
[PXUIField(DisplayName = "Order ID", Visibility = PXUIVisibility.Invisible)]
public virtual int? OrderID { get; set; }
public abstract class orderID : PX.Data.BQL.BqlInt.Field<orderID> { }
#endregion
```

The abstract inner class (lowercase `orderID`) is the BQL field descriptor — it is what you reference in `PXSelect` and `Where` clauses. The concrete property (uppercase `OrderID`) is the CLR property the platform uses to get and set values.

<Note>
`PXDBIdentity` columns are assigned by the database on insert and are never editable on screen. Mark the `PXUIField` visibility as `Invisible` or omit it from the UI entirely; display the natural key field (see the next step) to users instead.
</Note>

### Add additional fields

With the primary key in place, add the business fields your table needs. Each field follows the same abstract-class / property pattern. Here is a representative set covering common scenarios:

```csharp
#region OrderNbr
[PXDBString(15, IsUnicode = true, IsKey = true, InputMask = ">CCCCCCCCCCCCCCC")]
[PXDefault]
[PXUIField(DisplayName = "Order Nbr.", Visibility = PXUIVisibility.SelectorVisible)]
[PXSelector(typeof(RSSVRepairOrder.orderNbr), Filterable = true)]
public virtual string OrderNbr { get; set; }
public abstract class orderNbr : PX.Data.BQL.BqlString.Field<orderNbr> { }
#endregion

#region CustomerID
[PXDBInt]
[PXDefault]
[PXUIField(DisplayName = "Customer")]
[PXSelector(
    typeof(AR.Customer.bAccountID),
    typeof(AR.Customer.acctCD),
    typeof(AR.Customer.acctName),
    SubstituteKey = typeof(AR.Customer.acctCD),
    DescriptionField = typeof(AR.Customer.acctName))]
public virtual int? CustomerID { get; set; }
public abstract class customerID : PX.Data.BQL.BqlInt.Field<customerID> { }
#endregion

#region Status
[PXDBString(1, IsFixed = true)]
[PXDefault(RSSVRepairOrderStatus.Open)]
[PXUIField(DisplayName = "Status")]
[PXStringList(
    new[] { "O", "I", "C" },
    new[] { "Open", "In Progress", "Closed" })]
public virtual string Status { get; set; }
public abstract class status : PX.Data.BQL.BqlString.Field<status> { }
#endregion

#region OrderDate
[PXDBDate]
[PXDefault(typeof(AccessInfo.businessDate))]
[PXUIField(DisplayName = "Order Date")]
public virtual DateTime? OrderDate { get; set; }
public abstract class orderDate : PX.Data.BQL.BqlDateTime.Field<orderDate> { }
#endregion

#region EstimatedAmount
[PXDBDecimal(2)]
[PXDefault(TypeCode.Decimal, "0.00")]
[PXUIField(DisplayName = "Estimated Amount")]
public virtual decimal? EstimatedAmount { get; set; }
public abstract class estimatedAmount : PX.Data.BQL.BqlDecimal.Field<estimatedAmount> { }
#endregion

#region Description
[PXDBString(255, IsUnicode = true)]
[PXUIField(DisplayName = "Description")]
public virtual string Description { get; set; }
public abstract class description : PX.Data.BQL.BqlString.Field<description> { }
#endregion
```

### Apply key attributes: PXCacheName and PXPrimaryGraph

You already added `PXCacheName` in Step 2. Now add `PXPrimaryGraph` so that the platform knows which graph (business logic controller) owns this DAC. This attribute drives the hyperlink behavior when the DAC appears in selectors or inquiry results:

```csharp
[Serializable]
[PXCacheName("Repair Order")]
[PXPrimaryGraph(typeof(RSSVRepairOrderMaint))]
public class RSSVRepairOrder : IBqlTable
{
    // ... fields ...
}
```

If you have not yet created the graph, you can add `PXPrimaryGraph` later. The customization will compile without it, but selectors that display records of this type will not be able to navigate to the detail screen.

Also add the standard audit fields so the platform can track who created and last modified each record:

```csharp
#region CreatedByID
[PXDBCreatedByID]
public virtual Guid? CreatedByID { get; set; }
public abstract class createdByID : PX.Data.BQL.BqlGuid.Field<createdByID> { }
#endregion

#region CreatedDateTime
[PXDBCreatedDateTime]
[PXUIField(DisplayName = "Created On", Enabled = false)]
public virtual DateTime? CreatedDateTime { get; set; }
public abstract class createdDateTime : PX.Data.BQL.BqlDateTime.Field<createdDateTime> { }
#endregion

#region LastModifiedByID
[PXDBLastModifiedByID]
public virtual Guid? LastModifiedByID { get; set; }
public abstract class lastModifiedByID : PX.Data.BQL.BqlGuid.Field<lastModifiedByID> { }
#endregion

#region LastModifiedDateTime
[PXDBLastModifiedDateTime]
[PXUIField(DisplayName = "Last Modified On", Enabled = false)]
public virtual DateTime? LastModifiedDateTime { get; set; }
public abstract class lastModifiedDateTime : PX.Data.BQL.BqlDateTime.Field<lastModifiedDateTime> { }
#endregion

#region tstamp
[PXDBTimestamp]
public virtual byte[] Tstamp { get; set; }
public abstract class tstamp : PX.Data.BQL.BqlByteArray.Field<tstamp> { }
#endregion
```

### Publish and verify the DB table is created

With the DAC complete, add it to your customization project and publish:

1. In the Customization Projects screen, open your project.
2. Navigate to **Files** and confirm the DAC `.cs` file is included. If you created the file directly in the project folder it is already tracked; otherwise use **Add File** to include it.
3. Click **Publish** (or **Publish All** if you want to deploy all projects).
4. After the publish completes, connect to the application database with SQL Server Management Studio (or your preferred DB client) and run:

```sql
SELECT TOP 1 * FROM RSSVRepairOrder;
```

If the table exists and the `SELECT` returns without error, the platform successfully created the schema. All columns you declared with `PXDB*` attributes appear as columns; fields declared with unbound attributes (`PXString`, `PXInt`, etc.) do not produce columns.

</Steps>

## Adding the DAC to the customization project

If you created the file outside the Customization Project editor (for example, directly in Visual Studio), you must register it:

1. Open the **Customization Projects** screen and select your project.
2. Go to the **Files** tab and click **Add File**.
3. Browse to `App_RuntimeCode/DAC/RSSVRepairOrder.cs` (the runtime code folder) or the path where you saved the file.
4. Save the project. The file now appears in the project manifest and will be included in every publish and package export.

<Note>
The Customization Framework stores runtime DAC files under `App_RuntimeCode` in the web application directory. If you edit the file directly in the Code Editor inside the platform UI, it is automatically tracked in the project — you do not need to add it manually.
</Note>
