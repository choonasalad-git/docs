Custom tables give you a first-class way to persist data that has no home in the standard ERP schema. Instead of working around missing fields with notes, attachments, or overloaded text columns, you define a dedicated database table by writing a Data Access Class (DAC) — a plain C# class that the platform compiles, maps to a real SQL table, and manages through the same object-relational machinery that drives every built-in screen. The result is data that behaves identically to any native ERP entity: it participates in BQL queries, supports relationships, renders on data-entry screens, and respects security roles.

## What custom tables are

A custom table is a user-defined relational table that lives in the same application database as every standard ERP table. You create it by authoring a DAC — a C# class that implements the `IBqlTable` marker interface and declares its columns as strongly-typed inner classes called _fields_. When you publish your customization, the platform inspects every DAC in the project and issues the necessary `CREATE TABLE` or `ALTER TABLE` statements automatically. You never write schema migration scripts by hand.

Each field in the DAC maps to a database column through a _field attribute_ such as `PXDBString` or `PXDBDecimal`. The attribute specifies the SQL type, length, nullability, and other column-level constraints. Alongside the DB-mapped attributes you add UI and behavior attributes — `PXUIField` to set a display name, `PXDefault` to supply a default value, `PXSelector` to attach a lookup — so that one class definition covers both the database schema and the screen behavior.

## How custom tables integrate with the ERP

Because your custom table lives in the same database, it is a full participant in the platform's data layer:

- **BQL queries** — You query custom DACs with the same Business Query Language (BQL) syntax used for built-in tables. Joins, subselects, and aggregate queries all work without any special configuration.
- **Graph (business logic controller) integration** — A `PXGraph`-derived class can declare a `PXSelect` view over your DAC just as it would for `SOOrder` or `ARInvoice`. The cache, events, and workflow engine operate identically.
- **Audit and row-level security** — Add a `PXDBTimestamp` field and the platform enforces optimistic concurrency. Assign the table to a module and access rights flow from the standard role-permission matrix.
- **Import/export** — Because the DAC is a first-class entity, the built-in Excel import, push notifications, and OData feed all recognize it without extra wiring.

## Common use cases

Custom tables are the right tool whenever you need to store structured, relational data that is not covered by an existing ERP entity or a simple DAC extension:

- **Extending vendor records with domain-specific data** — Track vendor certifications, insurance expiry dates, or compliance scores in a dedicated table linked to the standard `Vendor` record by account ID.
- **Job and project tracking** — Store custom job phases, milestone checkpoints, or field-service visit logs that map to projects or service orders but require their own line-level detail.
- **Custom approval workflows** — Build an approval queue table that records approver, timestamp, status, and comments for any entity type without touching the standard workflow engine's schema.
- **Lookup and configuration tables** — Define controlled vocabularies — equipment categories, cost codes, region codes — that multiple screens reference through `PXSelector` lookups.
- **Integration staging** — Persist inbound data from external systems in a staging table before it is validated and promoted to native ERP records.

## Custom tables vs. DAC extensions

Both features let you add custom fields to the system, but they serve different purposes. Use the table below to decide which approach fits your requirement.

| Consideration | Custom table | DAC extension |
| --- | --- | --- |
| **Data belongs to** | A brand-new entity (no existing table fits) | An existing ERP entity (e.g., `Customer`, `SOOrder`) |
| **Database impact** | Creates a new SQL table | Adds columns to an existing SQL table |
| **Ownership** | You own the full schema | You extend a schema you do not own |
| **Relationships** | You define all keys and lookups | Foreign key to the parent table is implicit |
| **UI integration** | Requires a new screen or a detail tab | Fields appear inline on the existing screen |
| **Upgrade risk** | Low — new table is isolated | Low — extension columns are separate from base columns |

Choose a **DAC extension** when you need a handful of extra fields on an existing record and want those fields to appear directly on the standard data-entry form. Choose a **custom table** when you need a new entity with its own primary key, multiple records per parent, or a standalone screen.
