Graph extensions are the primary mechanism for customizing behavior on existing ERP screens. Instead of modifying the base graph's source code — which would be overwritten on every ERP upgrade — you create a `PXGraphExtension<TGraph>` subclass that sits alongside the base graph and adds or overrides only what you need. The framework wires your extension in automatically at runtime, so from the user's perspective the screen behaves as one cohesive unit.

## What a Graph Extension Does

A graph extension can do everything the base graph can do, scoped to a specific base graph type:

- **Add new data views** — declare additional `PXSelect<>` properties to display new grids or form panels on the screen.
- **Add new actions** — declare `PXAction<>` properties to introduce new toolbar buttons with their own permission controls.
- **Override or supplement event handlers** — respond to the same `RowSelected`, `RowInserted`, `FieldVerifying`, and other cache events that the base graph handles, either in addition to or instead of the base logic.
- **Add DAC cache extensions** — reference `PXCacheExtension` fields that extend the screen's primary DAC.

None of this requires access to the base graph's source code, and nothing you write in an extension modifies the base graph's compiled assembly.

## Anatomy of a PXGraphExtension

```csharp
public class SOOrderEntryExt : PXGraphExtension<SOOrderEntry>
{
    // 1. Additional data view linked to the current sales order
    public PXSelect<MyCustomRecord,
        Where<MyCustomRecord.orderNbr,
              Equal<Current<SOOrder.orderNbr>>>>
        CustomRecords;

    // 2. Custom action added to the toolbar
    public PXAction<SOOrder> SendForApproval;

    [PXButton(CommitChanges = true)]
    [PXUIField(DisplayName = "Send for Approval", MapEnableRights = PXCacheRights.Update)]
    protected virtual IEnumerable sendForApproval(PXAdapter adapter)
    {
        SOOrder order = Base.Document.Current;
        if (order == null) return adapter.Get();

        // Custom approval routing logic
        SOOrderEntryExtHelper.SendApprovalRequest(Base, order);

        Base.Document.Cache.SetValueExt<SOOrderExt.usrApprovalStatus>(
            order, ApprovalStatus.pending);
        Base.Save.Press();

        return adapter.Get();
    }

    // 3. Event handler responding to row selection
    protected virtual void _(Events.RowSelected<SOOrder> e)
    {
        SOOrder row = e.Row;
        if (row == null) return;

        // Enable or disable the custom action based on order status
        bool canSend = row.Status == SOOrderStatus.hold;
        SendForApproval.SetEnabled(canSend);
    }

    // 4. React to a field change on the base DAC
    protected virtual void _(Events.FieldUpdated<SOOrder, SOOrder.customerID> e)
    {
        SOOrder row = e.Row;
        if (row == null) return;

        // Clear the custom approval status when the customer changes
        e.Cache.SetValueExt<SOOrderExt.usrApprovalStatus>(row, null);
    }
}
```

## Extension Initialization and the Base Property

When the framework instantiates `SOOrderEntry`, it also instantiates every registered extension for that graph type in order. Your extension's `Initialize()` virtual method is called once immediately after construction, before any views are populated. Override it to perform one-time setup:

```csharp
public override void Initialize()
{
    base.Initialize();

    // Adjust the display name of a base view's column at runtime
    PXUIFieldAttribute.SetDisplayName<SOOrder.orderDate>(
        Base.Caches<SOOrder>(), "Requested Date");
}
```

The `Base` property gives you a typed reference to the base graph instance. Use `Base` to access the base graph's views, caches, actions, and any public helper methods:

```csharp
// Access a base graph view
SOOrder currentOrder = Base.Document.Current;

// Trigger a base graph action programmatically
Base.Save.Press();

// Access the cache for a base DAC
Base.Caches<SOOrder>().SetValueExt<SOOrder.status>(order, SOOrderStatus.open);
```

Do not store a local copy of `Base` in an instance field — the reference is always available through the property and caching it can lead to stale-reference bugs if the framework refreshes the extension chain.

## Multiple Extensions and Extension Chaining

More than one extension can target the same base graph. The framework supports this through an ordered **extension chain**. When a `RowSelected` event fires, for example, the framework calls:

1. The base graph's handler (if any).
2. Extension #1's handler (in registration order).
3. Extension #2's handler.
4. …and so on through all registered extensions.

Each handler in the chain can call `e.CallBase()` to explicitly invoke the previous handler in the chain, or simply return to skip the rest of the chain (for overriding scenarios):

```csharp
protected virtual void _(Events.RowPersisting<MyCustomRecord> e)
{
    if (e.Operation == PXDBOperation.Insert)
    {
        // Custom validation before the record is saved
        if (string.IsNullOrWhiteSpace(e.Row.Description))
            throw new PXException("Description is required.");
    }

    // Allow the rest of the chain (and base logic) to continue
    e.CallBase();
}
```

You can also call extension methods from another extension using the `GetExtension<TExt>()` helper:

```csharp
// Inside SOOrderEntryExt2, call a method defined in SOOrderEntryExt
var ext1 = Base.GetExtension<SOOrderEntryExt>();
ext1.SomePublicHelperMethod(order);
```

<Warning>
  **Extension ordering matters — manage it carefully.** The framework applies extensions in the order they appear in the Customization Project's manifest. If two extensions both override the same event (for example, `RowPersisting<SOOrder>`) and neither calls `e.CallBase()`, the last extension to run effectively silences all previous handlers — including base ERP validation logic. Always call `e.CallBase()` unless you have a deliberate reason to suppress the rest of the chain, and document that decision clearly. When you have multiple projects deployed simultaneously, each project's extensions are chained together in project publish order, which is another source of unexpected behavior. If you observe an event handler appearing to do nothing, check that an earlier extension in the chain is not swallowing the call.
