Even well-structured customizations encounter errors at some point—during a publish, after an ERP upgrade, or the first time a new workflow is exercised by a real user. Most errors fall into a small number of predictable categories, and each category has a characteristic set of root causes and fixes. Use this reference to identify the type of error you are seeing and follow the steps to resolve it. For errors that occur at publish time, always start by reading the full publish log (**Customization > Customization Projects > Publish Log**) before attempting any fix.

<Accordion title="Compile Errors">

Compile errors prevent the publish from completing. They appear immediately in the publish log with file name, line number, and a C# compiler error code. Fix all compile errors before addressing any other category.

### CS0246 — Type or namespace not found

**What causes it:** A class, interface, or namespace referenced in your code does not exist in any of the assemblies referenced by the project. Common triggers are:
- An ERP upgrade renamed or removed a base class.
- A `using` directive references a namespace that no longer exists.
- A required third-party assembly is not present in the application's `bin` folder.

**How to fix it:**
1. Note the full type name from the error message.
2. Use the ERP release notes or your IDE's object browser to find the type's current namespace and assembly.
3. Update the `using` directive or add the assembly reference to the project.
4. If the type was removed entirely, replace the usage with the current equivalent API.

---

### CS0012 — Missing assembly reference

**What causes it:** Your code references a type that exists in a specific assembly, but that assembly is not listed as a reference in the Customization Project. This differs from CS0246 in that the type exists—it just isn't reachable.

**How to fix it:**
1. In the Customization Project editor, open the **References** section.
2. Add the missing assembly (`.dll`) by clicking **Add Reference** and selecting the file from the application's `bin` directory.
3. Re-validate the project to confirm the error is resolved.

---

### CS0104 — Ambiguous name reference

**What causes it:** Two different namespaces in your `using` directives both define a type with the same name. For example, both `PX.Data` and a third-party library define a class called `Attribute`.

**How to fix it:**
1. Replace the short type name with its fully qualified name in the conflicting line.
2. Alternatively, add an alias for one of the namespaces at the top of the file:
   ```csharp
   using PXData = PX.Data;
   ```
3. If the ambiguity is widespread, remove the less-used `using` directive and qualify those references instead.

</Accordion>

<Accordion title="Publish Errors">

Publish errors occur after compilation succeeds, during the schema migration or sitemap update phases. They appear in the publish log after the compile output.

### DB conflict — Column already exists with incompatible type

**What causes it:** A DB script in your project tries to add a column that already exists in the database with a different data type or length, or a previous partial publish left the schema in an inconsistent state.

**How to fix it:**
1. Connect to the database with a SQL client and inspect the current column definition:
   ```sql
   SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH
   FROM INFORMATION_SCHEMA.COLUMNS
   WHERE TABLE_NAME = 'YourTableName' AND COLUMN_NAME = 'YourColumnName';
   ```
2. If the existing column type is acceptable, update the DB script in your project to use `ALTER COLUMN` instead of `ADD COLUMN`, or add a conditional check:
   ```sql
   IF NOT EXISTS (
     SELECT 1 FROM INFORMATION_SCHEMA.COLUMNS
     WHERE TABLE_NAME = 'YourTableName' AND COLUMN_NAME = 'YourColumnName'
   )
   BEGIN
     ALTER TABLE YourTableName ADD YourColumnName NVARCHAR(50) NULL;
   END
   ```
3. If the existing column has the wrong type from a previous bad deploy, migrate the data first, drop the column, then let the script recreate it.

---

### Duplicate screen ID

**What causes it:** Your project registers a new screen with an ID (for example, `XX000000`) that is already registered—either by another customization project or by the base ERP application.

**How to fix it:**
1. In the **Customization Projects** screen, open the conflicting project and navigate to **Screens**.
2. Verify that the screen ID you chose does not conflict with an existing screen. Use the **XX** prefix convention (or your organization's designated prefix) and check the full list of registered screens in the sitemap.
3. Assign a unique ID to your screen and update all navigation links that reference the old ID.

---

### Missing sitemap parent

**What causes it:** Your project adds a new sitemap entry as a child of a parent node that does not exist—for example, a custom workspace that was removed in a previous unpublish or that has not yet been created.

**How to fix it:**
1. Open the **Sitemap** section of the Customization Project editor.
2. Check the **Parent** field of the failing entry and confirm that the parent node ID matches an existing node in the ERP sitemap.
3. If the parent is another custom workspace from a different project, ensure that project is published before this one by adjusting **Publish Order**.

</Accordion>

<Accordion title="Runtime Errors">

Runtime errors occur after a successful publish, when users interact with the application. They typically surface as a red error banner or an exception dialog in the ERP UI.

### NullReferenceException in an event handler

**What causes it:** Your event handler accesses a property on `e.Row` without first checking whether `e.Row` is null, or it calls a method on a cache-retrieved object that returned null.

**How to fix it:**
1. Add a null guard at the top of every event handler that accesses `e.Row`:
   ```csharp
   protected void SOOrder_RowSelected(PXCache cache, PXRowSelectedEventArgs e)
   {
       SOOrder row = e.Row as SOOrder;
       if (row == null) return;

       // Safe to access row properties below
   }
   ```
2. For objects retrieved from the cache or from a `PXSelect`, always check for null before dereferencing:
   ```csharp
   SOOrder order = SOOrder.PK.Find(Base, orderType, orderNbr);
   if (order == null)
   {
       throw new PXException(Messages.OrderNotFound);
   }
   ```
3. Check the application trace log (**Tools > Trace**) for the full stack trace to identify exactly which line threw the exception.

---

### PXException message appearing in the UI

**What causes it:** Business logic in your graph or event handler deliberately throws a `PXException` with a user-facing message. This is expected behavior, but if the message is confusing or incorrect, the underlying logic needs review.

**How to fix it:**
1. Read the full exception message shown in the UI and cross-reference it with your `PXException` throws in the codebase.
2. Verify that the condition triggering the exception is genuinely invalid. If it is a false positive (the exception fires for a valid user action), add the missing condition that should allow the action.
3. If the message text is unclear, update the string in your `Messages` class to a more descriptive, actionable description.

</Accordion>

<Accordion title="BQL Errors">

BQL (Business Query Language) is the strongly-typed query language used to retrieve ERP data. BQL errors often manifest as compile errors with long, generic-looking type messages, or as runtime exceptions when a query is executed.

### Type mismatch in BQL `Where` clause

**What causes it:** A BQL parameter or constant uses a different .NET type than the DAC field it is being compared to. For example, comparing a `string` constant to an `int` field.

**How to fix it:**
1. Find the DAC definition for the field involved and confirm its `IBqlField` type (the inner interface type, such as `BqlString` or `BqlInt`).
2. Ensure your constant or parameter uses the matching BQL type:
   ```csharp
   // Incorrect: comparing an int field with a string constant
   .Where<SOOrder.status.IsEqual<PX.Data.BQL.BqlString.Constant<"N">>>

   // Correct: status is a string field, so BqlString is correct
   .Where<SOOrder.status.IsEqual<SOOrder.status.AsField>>
   ```
3. Use fluent BQL where possible—it provides better compile-time type checking than classic BQL syntax.

---

### Field not found in DAC

**What causes it:** A BQL query references a field (inner class on a DAC) that does not exist in the DAC definition. This commonly happens after an ERP upgrade renames a field or after a refactor that removed a custom field.

**How to fix it:**
1. Open the DAC definition (or its extension) and confirm the field class name matches what your BQL query uses.
2. If the field was renamed in the base ERP DAC, update every BQL reference to use the new name.
3. If the field is a custom field on a DAC extension, make sure you are referencing it through the extension type:
   ```csharp
   // Referencing a custom field on a DAC extension
   .Where<SOOrderExtension.usrCustomField.IsEqual<True>>
   ```

---

### Incorrect `Where` clause type nesting

**What causes it:** Classic BQL `Where` clauses use generic type nesting that is easy to mis-order, resulting in compile errors that are difficult to read.

**How to fix it:**

Migrate the query to fluent BQL syntax, which is significantly easier to read and debug:
```csharp
// Classic BQL — hard to read, easy to get nesting wrong
PXSelect<SOOrder,
    Where<SOOrder.status, Equal<SOOrderStatus.open>,
        And<SOOrder.customerID, Equal<Required<SOOrder.customerID>>>>>

// Fluent BQL — same query, clearer structure
PXSelect<SOOrder,
    Where<SOOrder.status.IsEqual<SOOrderStatus.open>
        .And<SOOrder.customerID.IsEqual<P.AsInt>>>>
```

</Accordion>

<Accordion title="Screen Errors">

Screen errors affect the rendering or interactive behavior of custom or modified screens. They range from fields that do not appear to selectors that return no results.

### Field not bound to the data source

**What causes it:** A control on the screen references a field name that does not exist on the primary DAC of the data view the container is bound to. This causes the field to render as blank and often logs a binding warning in the application trace log.

**How to fix it:**
1. Open the screen in the Customization Project's **Layout Editor**.
2. Select the unbound control and inspect its **Data Field** property.
3. Confirm the field name exactly matches a property (case-sensitive) on the DAC. If the field is on a DAC extension, make sure the data view's DAC type includes the extension.
4. If the field is genuinely new, add it to the DAC and DAC extension before adding it to the screen.

---

### Selector not returning results

**What causes it:** A `PXSelector` field displays a lookup but the dropdown is empty or does not show the expected records. Common causes are an overly restrictive `Where` clause on the selector, a missing join condition, or a data view delegate that filters out all records.

**How to fix it:**
1. Locate the DAC field definition for the selector and inspect its `PXSelector` attribute:
   ```csharp
   [PXSelector(typeof(Search<InventoryItem.inventoryID,
       Where<InventoryItem.itemStatus, Equal<InventoryItemStatus.active>>>),
       typeof(InventoryItem.inventoryCD),
       typeof(InventoryItem.descr))]
   ```
2. Temporarily remove the `Where` clause and republish to confirm records exist in the base table. If records appear without the filter, tighten the filter incrementally until you find the condition that is excluding valid records.
3. If the selector uses a `Search` against a view with a delegate, add `PXTrace.WriteInformation` logging inside the delegate to output the record count at runtime.

---

### Control width and layout issues

**What causes it:** A custom control overlaps adjacent fields or is truncated because its width or column span is not configured correctly in the Layout Editor.

**How to fix it:**
1. Open the screen in the **Layout Editor** within the Customization Project editor.
2. Select the affected control and adjust its **Width** and **ColSpan** properties to match the surrounding layout grid.
3. Use the **Preview** button to see the rendered result before publishing. Verify the layout at both standard (1280px) and compact (1024px) browser widths.

</Accordion>
